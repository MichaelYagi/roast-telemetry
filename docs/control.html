Controlling a roast, and its safety limits

For roasters the app can write to (Direct Modbus, Aillio Bullet, TC4+ and the built-in simulators), you can change the heater, fan and drum by hand, and the app can also do it for you: repeat a saved roast's settings, or hold a target by adjusting the heater. Every one of those changes passes through the same safety limits, and there is an Emergency stop button on the Live Roast page.

Read this first. These are the app's own safety features, and they only work while the app can still talk to the roaster. They are not a substitute for the roaster's own protection (its physical stop, over-temperature cut-offs, airflow interlocks). If the cable is unplugged, the computer freezes or the power drops, the app cannot switch anything off, and what happens next is decided entirely by the machine. See Before you use this on a real roaster.

What has been tested

All of this is covered by automated tests, including runs against the built-in simulated FZ-94 through the real Modbus code path. It has not yet been tried on a real roaster. Only the FZ-94's read and write connection has been checked on real hardware. The starting values for target control in particular are conservative guesses, not settings tuned for any real machine.

Safety limits

Settings → Roaster safety. They apply to every command that reaches the roaster: the sliders, alarm rules, repeating a saved roast and target control alike.

LimitDefaultWhat it does
Heater never above (%)100Any heater command above this is lowered to it.
Fan never below while heating (%)0While the heater is on, the fan can't be set (or left) below this. Turning the heater on with the fan too low raises the fan too.
Drum never below while heating (%)0The same rule for the drum.
Fan level in an emergency (%)100What the fan is set to by the Emergency stop and the automatic fail-safes.
Heater off if nobody has the roast open for (seconds)120See Automatic fail-safes. 0 turns it off.

While a heater limit below 100% is set, the burner temperature setpoint (the direct-°C slider on machines that have one) is refused, because a temperature can't be checked against a percentage cap. Use the heater slider. Limits are read when a roast starts and again whenever automatic control or the Emergency stop is used.

Emergency stop

A red button above the chart on the Live Roast page (full width on a phone). It sets the heater to 0 and the fan to the emergency level, stops any automatic control and cancels any delayed alarm-rule actions. The drum keeps turning. The roast keeps recording so nothing already logged is lost, and a “Safety: emergency stop” marker is added to the chart.

If the app can't reach the roaster, the button says so (“Couldn't reach the roaster”) — switch it off at the machine.

Automatic fail-safes

Each of these puts the roaster in the same safe state as the Emergency stop (heater 0, fan at the emergency level) and leaves a “Safety: …” marker on the chart.

TriggerWhat happens
The heater is on and no browser has the roast open for the watchdog time (default 120 s)Safe state. Applies even while automatic control is running: an unattended heater is the case this exists for. Set it to 0 to turn it off.
An error stops the roast (for example the connection to the roaster breaks)The app tries to switch the heater off before it lets go, then ends the roast as aborted.
Target control loses the bean-temperature reading for more than 10 secondsSafe state: it won't keep heating blind.
A write during automatic control failsSafe state.
You end the roast (OFF) with the heater onThe heater is switched off; the fan and drum are left as they are.

After a fail-safe the Live Roast page shows why, and the heater stays off until you move a slider or start automatic control again.

What they can't do

  • They can't act if the app can't reach the roaster. A written “heater off” never arrives over an unplugged cable, and the machine keeps doing whatever it was last told, unless it has its own timeout.
  • They don't run if the computer running the server crashes or loses power, or after the server process is killed.
  • They can't override the roaster's own panel: turning something up at the machine still works.

Automatic control

On the Live Roast page, the Automatic control panel. Both kinds start at Charge (they wait until Charge is marked), keep the current settings until then, and time everything from Charge. Moving any slider by hand takes over: automatic control stops. Alarm rules don't cancel it.

Repeat a saved roast

Pick any finished roast that recorded its heater, fan or drum settings. The app turns those recordings into steps timed from that roast's Charge: a step is added each time a value moved by at least 2%, so small wobbles don't become dozens of writes. Repeating a roast whose file has no recorded controls is refused, because a file that never recorded them reads back as zeros, which would switch the heater and fan off at Charge. Automatic control keeps the last values after the final step. It does not end the roast for you.

Through the API you can also send your own steps (time in seconds from Charge; heater, fan and drum values; and a ramp flag to move smoothly from the previous step instead of jumping).

Hold a target

Choose rate of rise or bean temperature, a target, and a heater maximum. The app adjusts the heater with a simple PI controller (it reacts to how far off the target is and to how long it has been off). It:

  • starts from the heater's current level, so switching it on doesn't cause a jump;
  • never changes the heater faster than 1% per second (adjustable through the API);
  • stays inside the heater minimum and maximum, and inside the safety limits;
  • stops by itself at Drop.

Rate-of-rise control needs about 18 seconds of readings after the roast starts before there is a rate to act on. Through the API the target can also be a curve (a list of seconds-from-Charge and value points, blended in between) and the two gains can be set.

Tuning: the built-in gains are gentle starting values. They behave well on a made-up model of a drum roaster (rate of rise settles on target; bean temperature settles within a few degrees, with some overshoot), but every roaster responds differently and none has been tuned. Try it on a small, cheap batch with your hand near the Emergency stop, and lower the heater maximum while you learn how it behaves.

Before you use this on a real roaster

The most useful check is to ask the machine's maker, or an owner who knows it well, what the machine does without the app:

  • If the controller stops sending commands, or the cable or USB link drops, does the machine keep its last heater setting, or does it have a communication timeout that switches the heater off?
  • What are its own limits: an over-temperature cut-off, a thermal fuse, an interlock that cuts the heater if the fan stops?
  • Does a command over the data link go through the same safety checks as the front panel, or can it bypass them?
  • What is the highest heater or setpoint value the data link accepts, and what happens when you write something outside its range?
  • What does it do after a power cut or restart: does it resume heating?
  • Does the physical stop or panel always win over a command from the data link?

Also worth doing: set the heater limit and the fan minimum in Settings to values you're comfortable with, try the Emergency stop and each fail-safe with the roaster empty first, and keep the roaster where you can reach its own stop.

Trying it without a roaster

Every control feature works on the built-in simulated devices. In the Configure Roast form, pick Direct Modbus and the “Try a simulated one” FZ-94, then press ON and START. See Getting started.

API

All under /api, for a live (connected) roast.

MethodPathPurpose
GET/roasts/{id}/controlWhat automatic control is doing, the current limits, the last commanded heater/fan/drum values, and why a fail-safe tripped (if one did)
POST/roasts/{id}/emergency-stopHeater 0, fan to the emergency level, automation stopped. Returns ok: false if the roaster couldn't be reached
PUT/roasts/{id}/control/programRun steps (time_s from Charge, heater_pct/fan_pct/drum_speed_pct, ramp)
POST/roasts/{id}/control/program/from-roastRepeat another roast's recorded settings (source_roast_id); 409 if it recorded none
PUT/roasts/{id}/control/feedbackHold a target: variable (bt or ror_bt), setpoint or curve, optional kp, ki, output_min_pct, output_max_pct, max_step_pct_per_s
DELETE/roasts/{id}/control/automationStop any automatic control; the roaster keeps its current settings
GET / PUT/settingsThe safety limits are the control object (heater_max_pct, fan_min_pct, drum_min_pct, safe_fan_pct, client_watchdog_s)

Read-only devices (the MS6514 thermocouple meter and .alog playback) refuse all of these. A manual command to /roasts/{id}/commands stops automatic control and is subject to the same limits.
