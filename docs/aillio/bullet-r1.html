Aillio Bullet R1

A genuinely different data source from everything else this app supports: the Bullet talks over a raw, vendor-specific USB protocol, not Modbus and not even a serial/COM port. There's no register map to configure and no port/host to type in — the app finds the roaster by its own USB vendor/product id and talks to it directly.

Only the R1 model is supported today. The R2 has a different USB product id and a materially different frame layout — it isn't just a different register map the way the FZ-94/FZ-94 Evo are related, so it needs its own protocol implementation, not reuse of R1's.

Install requirements

Needs pyusb plus a native libusb shared library — already part of this project's own backend/requirements.txt, so a plain pip install -r backend/requirements.txt covers it.

  • Linux/macOS — no extra step needed in most cases; a system libusb is typically already present, and pyusb falls back to a bundled one otherwise.
  • Windows — needs the roaster's USB driver swapped to a generic libusb-compatible one before this app can see it at all (the OS's own default driver claims the device exclusively otherwise). Zadig is the standard tool for this — plug the Bullet in, run Zadig, select the Bullet's USB interface, and install the libusb-win32 (or WinUSB) driver over the default one. This is a one-time step per machine, but it's a real, manual one — unlike every other data source this app supports, which only ever need a COM port.

Connecting

Configure Roast → Data source → Aillio Bullet (USB) → Device tab → Model → Bullet R1. That's the entire configuration — press ON once the roaster is plugged in and its driver is set up.

Heater/Fan/Drum read back the device's own last-reported state (not an echo of this app's own commands), same "don't clobber real state on connect" behavior as Direct Modbus — see Getting started → The data sources.

Protocol confidence

Aillio has never published an official protocol specification for this device. The register offsets, opcodes, and control semantics this app uses were traced directly from the manufacturer's own shipped roaster-scope driver source (not guessed, not reverse engineered from scratch) — see aillio_bridge/r1.py's own module docstring for the full byte-level detail. Not tested against real Bullet R1 hardware in this project's own development environment (none available) — the logic is a faithful port of that confirmed source, but hasn't been independently verified against a physical unit here. If something doesn't match real behavior, that's the most likely place to look first.

Known limitations

  • R1 only — R2 support needs its own research pass and protocol implementation; not yet built.
  • No fake-hardware test rig. Every other live-hardware mode this app supports has a standalone fake process you can point the app at instead of real hardware (see hardware_fakes/) — those all work by standing in on the other end of a real OS-level channel (a virtual serial port, a TCP socket) the real client already knows how to open. Raw USB has no equivalent generic channel; convincingly faking a real USB device needs kernel-level emulation, well beyond what the other fakes need. This is instead covered by thorough backend pytest coverage of the protocol decoding/command-building logic itself (pure functions, no hardware or even pyusb involved — see tests/test_aillio_r1_protocol.py and tests/test_aillio_engine.py), just not something you can click through in a running instance of the app without a real Bullet.
  • No milestone-triggered automation rules (the Artisan-Alarms-style bindings Direct Modbus has) — not extended to this mode. Milestones are always manual clicks here, same as Direct USB (thermocouple meter).
