Getting started

Setup and the run command differ slightly by platform — find yours below, then the rest of this page (accounts, data sources, saving a roast...) is the same regardless.

Setup & run

Run it on whichever computer is physically connected to the roaster. For every USB/serial data source (Direct Modbus RTU, MS6514, TC4+, Aillio Bullet) the server process itself needs the OS to see that serial/USB port directly — it can't reach across a network to a port plugged into a different machine. Other devices on your network (a phone, another computer) can still view/control an already-running roast remotely — that's what --lan / -Lan (listening on 0.0.0.0) is for — but that's about who can reach the server once it's running, not about which machine the server itself has to run on. The one exception: Direct Modbus over Ethernet (e.g. FZ-94 Evo) is genuinely network-connected, so the server can run on any machine that can reach its IP address.

Also worth weighing before turning on LAN access at all: this app can send real Burner/Air/Drum/Heater commands to a real, heat-producing machine — anyone who can reach 0.0.0.0 on your network can too, with nothing beyond the login screen standing between them and a roaster mid-roast. Fine on a trusted home network; worth real thought anywhere less trusted.

From a terminal: scripts/install.sh once (or scripts\install.ps1 on Windows), then scripts/run-server.sh (or scripts\run-server.ps1) whenever you want to run it — the app is then at http://localhost:8000. What every script does, and its options, is in the Scripts reference below.

Windows — PowerShell (native)

Only worth it for one specific reason: reaching a real roaster's actual COM port directly. WSL doesn't expose USB serial devices without extra tooling (usbipd-win), so if you're connecting to a real FZ-94 (or any real Modbus roaster) over USB, this is the recommended path over WSL2. 

cd roast-telemetry
scripts\install.ps1
scripts\run-server.ps1

install.ps1 installs Python/Node.js themselves too (via winget, asking first) if either is missing, then creates the venv and installs everything below — so this is the whole setup, not just a shortcut for part of it. It also offers to set up WSL2 (if present) for fake-hardware.sh, the fake-hardware testing tool — skipped automatically if WSL2 isn't installed; the app itself never needs it. Add -Yes to run it unattended (no prompts — it answers yes to the required Python/Node installs and skips the optional WSL2 offer). Equivalent by hand: 

python -m venv .venv-windows
.venv-windows\Scripts\Activate.ps1
pip install -r backend\requirements.txt
cd frontend; npm install; cd ..
Note: if Activate.ps1 refuses to run ("running scripts is disabled on this system"), run once: Set-ExecutionPolicy -Scope CurrentUser RemoteSigned, then retry. Requires Python and Node.js installed natively on Windows — a venv created inside WSL only runs inside WSL (its files are Linux binaries), it's not usable from PowerShell even though the files are visible from Windows too if the repo sits under a Windows-mounted path.

scripts\run-server.ps1 takes the same options as the WSL2/Linux/macOS script below, PowerShell-flavored: -Port 7890, -Reload, -SkipBuild, -ForceBuild, and -Lan (reachable from other devices on your network — -BindHost 0.0.0.0 is the same thing spelled out; it's not called -Host because PowerShell reserves that name). Windows may ask to allow Python through its firewall the first time you use -Lan.

Windows (WSL2) / Linux

cd roast-telemetry
scripts/install.sh
scripts/run-server.sh

install.sh installs Python 3.10+/Node.js/socat themselves too (via apt-get, asking first) if any are missing, then creates the venv and installs everything below. Equivalent by hand: 

python3 -m venv .venv && source .venv/bin/activate   # first time only
pip install -r backend/requirements.txt               # first time only
cd frontend && npm install && cd ..                   # first time only

scripts/run-server.sh takes a port number (scripts/run-server.sh 7890, default 8000), --reload (auto-restart on backend code changes), --lan (or --host 0.0.0.0; reachable from other devices on your network), and --skip-build / --force-build (see the callout below). install.sh --yes runs the setup unattended (no prompts — it answers yes to the required Python/Node installs, so it will run sudo apt-get/brew without asking; optional extras like socat are skipped).

Note: if this repo lives under a Windows-mounted path in WSL (e.g. /mnt/c/...), filesystem change events don't propagate to Vite's watcher, so Hot Module Reload can silently serve stale code after an edit. vite.config.js already sets server.watch.usePolling to work around this — if you still see stale behavior, restart npm run dev.

Linux / Raspberry Pi (server only)

On Linux — a Raspberry Pi running Raspberry Pi OS included — the app runs as a plain server you open in a browser, using the same two scripts as above. There's no .deb/.rpm/AppImage package: for a server-only app those would save little over install.sh + run-server.sh, and the scripts already cover the real setup work. Over SSH, unattended: 

scripts/install.sh --yes
scripts/run-server.sh --lan     # then open http://<this machine's address>:8000 from another device
  • Serial roasters (Direct Modbus over USB, MS6514, TC4+): your user needs permission to open the serial port. On Debian-based systems (Raspberry Pi OS, Ubuntu) that means being in the dialout group: sudo usermod -aG dialout $USER, then log out and back in. USB-direct devices (Aillio Bullet) have their own requirements — see Aillio Bullet R1.
  • The server has to run on the computer the roaster is plugged into — here, that's the Pi. See the note at the top of this page, which also covers the safety side of --lan.
  • It runs in the foreground. Use something like tmux or a systemd service if you want it to survive closing the terminal or a reboot — no ready-made service file is included. The first start builds the frontend, which is the slow part on a small board; later starts skip it unless the source changed.

macOS

Same script as WSL2/Linux above (it detects macOS and uses brew instead of apt-get):

cd roast-telemetry
scripts/install.sh
scripts/run-server.sh

Equivalent by hand:

python3 -m venv .venv && source .venv/bin/activate   # first time only
pip install -r backend/requirements.txt               # first time only
cd frontend && npm install && cd ..                   # first time only

Real USB serial access (for a real roaster) works natively on macOS with no equivalent of WSL's USB-passthrough problem. For the fake hardware below, socat installs via brew install socat (or let install.sh offer to do it).

Whichever platform: open http://localhost:8000 — one process, one port. The API lives under /api/* on the same port (docs still at /docs), and any other path falls back to the React app's index.html so client-side routing (/roasts/:id, /compare, etc.) works on a hard refresh too.

Note: the run scripts rebuild the frontend before starting when it's out of date, since the backend serves whatever's already sitting in frontend/dist/ and never rebuilds it for you — a stale build silently keeps serving old code with no error of any kind, including old login/auth behavior (this is a real thing that happened: an old pre-login build let anyone straight into the app with no login screen, even though the backend itself correctly rejected every API call underneath it). "Out of date" means frontend/dist/ is missing, or something under frontend/src, public, index.html, vite.config.js or package.json is newer than the last build — so a restart with nothing changed doesn't pay for a rebuild. --force-build/-ForceBuild rebuilds regardless (e.g. after npm install changed dependencies without touching package.json); --skip-build/-SkipBuild never does. Equivalent to running cd frontend && npm run build && cd .. && PYTHONPATH=. uvicorn backend.app.main:app --port 8000 by hand.

Two ports (for frontend development)

Use this instead when you're actively editing the frontend and want Vite's hot-reload rather than rebuilding on every change.

Backend

scripts/run-server.sh --skip-build --reload

(scripts\run-server.ps1 -SkipBuild -Reload on native Windows PowerShell.) --skip-build/-SkipBuild since Vite (not this backend) is serving the frontend here — nothing to build/serve from frontend/dist/ in this flow. --reload/-Reload auto-restarts the backend on backend code changes.

Docs at http://localhost:8000/docs. Roast data persists to backend/data/roasts.db (SQLite index) and backend/data/roasts/*.alog (full profiles). A pre-baked example lives at backend/data/sample_roasts/demo_roast.alog for exercising playback mode.

Frontend

cd frontend
npm install
npm run dev

Opens on http://localhost:5173 and proxies /api/* (including WebSockets) to the backend on port 8000 — see frontend/vite.config.js. Same on every platform.

The Live Roast screen is laid out like a roasting-scope screen: a toolbar with the title, ON/OFF device toggle + START recording button, and digital elapsed-time clock; vertical control sliders (Burner/Air/Drum, plus Burner SV in native °C for modbus_live) beside the banded live chart, with color-coded ET (crimson) / BT (blue) curves and a matching ET/BT/ΔBT readout column; and the CHARGE/DRY END/FC START/FC END/SC START/DROP manual event-marker buttons underneath the chart. DRY%/»DRY/»FCs and other milestone-derived readouts are available as optional items in the configurable Breakout Panel (Settings) rather than a fixed row.

Accounts and access

Opening the app for the first time shows a login/register screen — there's no built-in default account. The very first person to register becomes the admin, with immediate access; every account registered after that starts pending and can't log in until the admin approves it from the Manage Access page (only visible to the admin). From there the admin can Allow a pending registration, Deny one (pending or already-allowed — denying an already-logged-in user ends their session immediately, not just on their next login attempt), send a denied account back to pending for reconsideration, or Delete an account outright.

There's no per-feature permission system beyond this one gate — every allowed account, admin or not, has full access to everything else in the app (all roast modes, history, settings, automation rules). Sessions are a plain httponly cookie, not a token stored in the browser's own JS-accessible storage, and login persists across a backend restart (accounts and sessions are both in the same SQLite file as everything else, backend/data/roasts.db).

For calling the API directly — a script, a Home Assistant integration, curl — without going through the browser's cookie-based login at all, click your username in the header to open Account and generate an API key. Send it as an X-API-Key header; it's an alternative credential alongside the session cookie, not a replacement for it (the browser app itself keeps using cookies). The key is shown in full exactly once, right when you generate/regenerate it — only its hash is stored, so neither this app nor its database can show it to you again afterward. Regenerate replaces it (the old one stops working immediately); Revoke turns off API-key access entirely without issuing a replacement.

The data sources

Every roast is driven by one of these modes, picked from the Configure Roast form's "Data source" dropdown:

  1. Simulator — a small thermal model that generates realistic BT/ET/RoR curves and auto-detects roast events (turning point, dry end, first crack, drop). No hardware needed.
  2. .alog Playback — loads a real roast log and replays it at real (or accelerated) speed, including its events and notes. Also reads real-world .alog files, not just this project's own.
  3. Direct Modbus (USB or Ethernet) — talks straight to a real roaster's PLC over Modbus. Ships with defaults for Coffee-Tech's FZ-94 (USB/RTU) and FZ-94 Evo (Ethernet/TCP); every register is overridable for a different Modbus roaster. See docs/modbus/.
  4. Direct USB (thermocouple meter) — reads a Mastech MS6514 dual K-type thermocouple meter straight over USB-serial. Read-only (the meter has no command channel); T1 → BT, T2 → ET.
  5. Aillio Bullet (USB) — talks straight to a real Aillio Bullet over its own vendor-specific USB protocol (not Modbus/serial at all). Ships with the R1 model; nothing else to configure per-install (no port/host, the app finds it by its own USB id). See docs/aillio/bullet-r1.html.
  6. TC4+ (USB, aArtisanQ/PID firmware) — plain ASCII serial commands over USB to a TC4+ shield. Real Heater/Fan control (this hardware has no Drum channel at all); no feedback readback for either, so writes are fire-and-forget. DIY hardware with no single default wiring/config, so unlike the rest of these it has no built-in preset.

Every live-hardware mode leaves every milestone (Charge, Dry End, FC Start, and the rest) to the operator's own click by default, rather than guessing them from the temperature curve the way the Simulator does — live RoR is still computed and shown either way, to help time the click. Charge/Dry End/FC Start can optionally be switched to auto-detect from BT instead (Configure Roast form, opt-in, off by default) — manual clicks still work as an override even with that on. Turning Point always auto-fires either way; it's a pure observation (the BT minimum right after Charge), not a judgment call.

Clicking ON connects to the device and starts streaming live readings (nothing recorded yet); START begins actually recording that stream into a roast — for modbus_live/ms6514_live/aillio_live/tc4_live these are two genuinely separate steps (verify the connection before committing to a roast). For simulator/alog_playback, connecting and recording happen together in one step, since there's no real external connection to verify first.

Built-in presets

"Load saved config" entries the app ships with, so most people never type in a register map or port by hand. Alphabetical by preset name; tested on real hardware means actually connected to and verified against the physical device, not just protocol-level unit tests or a fake — everything else here is well-tested in every other sense (real end-to-end tests against hardware_fakes/, or thorough protocol-decoding pytest coverage for Aillio), just not yet against its real hardware.

More machine support is planned over time, covering a wide range of roasters/meters. In practice that mostly isn't new engine code: a new Modbus roaster model is usually just a new Device Profile (register numbers as data, not code); a genuinely different protocol (raw USB like Aillio, plain serial commands like TC4+) gets its own thin engine sharing the same core contract (tick/apply_command/status/close/is_finished) every other data source already implements. If your roaster or meter isn't listed above, it's very likely addable without a rewrite.

Saving a roast

Automatic — nothing extra to do. Click OFF once you're done: that stops the roast and writes its .alog file to backend/data/roasts/<roast_id>.alog, regardless of how it ends ("complete" if the engine itself signaled done, "stopped" if you clicked OFF yourself, "aborted" if something actually went wrong). To get the file:

  1. Click View detail (next to the toolbar once finished), or find the roast under History.
  2. Click Download .alog at the top of the detail page.

Testing without real hardware

Simplest: pick a simulated device in the app. In Configure Roast, under Device, the port (or host) field has a Try a simulated one link — for the FZ-94, FZ-94 Evo, MS6514 and TC4+. It fills in a sim://… value; connecting starts a built-in fake of that machine inside the server, so there is nothing to install or start, on Windows, macOS or Linux. The roast is marked Simulated, tagged simulated automatically, and left out of History's averages, so it never skews your real numbers. (The Aillio Bullet has no simulated device — it is a raw USB device.) While connected but not yet recording, a simulated machine holds at its Charge readings; its roast starts the moment you press START, so however long you spend checking the connection first, the recording begins at Charge. The standalone fakes below are only for developers who want a fake running on its own, or a real virtual serial port.

simulator and alog_playback need nothing extra — fully self-contained. Three of the four live-hardware modes (modbus_live, ms6514_live, tc4_live — see aillio_live's own note further down) can each be exercised end-to-end, through the app's actual connection code, using a fake standing in for the real device. The fake itself always runs via scripts/fake-hardware.sh in WSL2/Linux/macOS (it depends on socat, which doesn't exist on Windows, for the serial-port-based fakes below — the Evo's own TCP fake needs no socat at all) — which flag you pass depends on where your app is running, not your own platform:

App running in WSL2/Linux/macOS (the WSL2/Linux/macOS setup above):

scripts/fake-hardware.sh fz94      # Coffee-Tech FZ-94, USB (Direct Modbus)
scripts/fake-hardware.sh evo       # Coffee-Tech FZ-94 Evo, Ethernet (Direct Modbus) -- no socat needed
scripts/fake-hardware.sh ms6514    # Mastech MS6514 meter (Direct USB)
scripts/fake-hardware.sh tc4       # TC4+, USB (aArtisanQ/PID firmware)

Prints a /tmp/... serial port (or, for evo, a host/port) to paste into the app's Configure Roast form.

App running natively on Windows PowerShell (the Windows — PowerShell setup above) — run this in WSL2 instead, add --tcp:

scripts/fake-hardware.sh fz94 --tcp      # default port 5020
scripts/fake-hardware.sh fz94 --tcp 5030 # or a specific port

Prints a socket://127.0.0.1:<port> URL to paste instead — a WSL-internal /tmp/... path isn't reachable from a native-Windows process at all, so this bridges to a TCP listener over WSL2's own localhost port forwarding instead (pyserial treats that URL as a live serial connection; verified working end to end — both reads and writes — against a real Modbus client). evo's own fake already speaks real Modbus TCP, so it needs no --tcp bridging at all — it works the same way regardless of where the app runs.

Either way it cleans up after itself on Ctrl+C, and picks a fresh port name every run. See the project's hardware_fakes/README.md for what it's doing under the hood, or docs/modbus/fz-94-usb.html for the FZ-94 one specifically (the one that can also be controlled — Burner/Air/Drum — not just read), including options this wrapper doesn't expose (like a separate drive port).

Aillio Bullet (aillio_live) has no fake — it's a raw USB device, not a serial port or a TCP socket, and convincingly faking a real USB device needs kernel-level emulation well beyond what the other fakes need. It's still thoroughly covered by the backend's own pytest suite (pure protocol-decoding tests, no hardware involved), just not something you can click through in a running instance of the app without a real Bullet. See docs/aillio/bullet-r1.html.

Scripts reference

Everything in scripts/ and what each is for. Not sure where to start? install.sh (install.ps1 on Windows) once, then run-server.sh (run-server.ps1).

ScriptPlatformWhat it does
install.shmacOS, Linux/WSL2First-time setup, safe to re-run. Checks for Python 3.10+ and Node.js (offers to install them via brew/apt-get — asks first), creates .venv, installs the backend dependencies and the frontend's npm packages, and offers socat (only fake-hardware.sh needs it). --yes runs it unattended.
