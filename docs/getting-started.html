Getting started

Setup and the run command differ slightly by platform — find yours below, then the rest of this page (accounts, data sources, saving a roast...) is the same regardless.

Setup & run

macOS, Linux, or Windows via WSL2 — open a terminal:

cd roast-telemetry
scripts/install.sh
scripts/run-server.sh

install.sh is one-time setup (installs Python/Node if missing, creates a venv, installs everything) — safe to re-run. run-server.sh starts the app at http://localhost:8000 — that's it. Full option reference for both: Scripts reference below.

Windows — native PowerShell

Only needed to reach a real roaster's COM port directly (WSL can't see USB serial devices without extra setup) — otherwise, use WSL2 above instead. 

cd roast-telemetry
scripts\install.ps1
scripts\run-server.ps1

Same idea as above, PowerShell-flavored. If Activate.ps1 refuses to run, once: Set-ExecutionPolicy -Scope CurrentUser RemoteSigned.

Raspberry Pi / headless Linux, over SSH: scripts/install.sh --yes, then scripts/run-server.sh --lan, then open http://<that machine's address>:8000 from another device. Using a serial roaster (Direct Modbus over USB, MS6514, TC4+)? Your user needs the dialout group first: sudo usermod -aG dialout $USER, then log out and back in.

Before using --lan / -Lan: the server still has to run on whatever machine the roaster's own USB/serial port is plugged into — other devices on the network can only view/control an already-running roast remotely, not reach a port on a different machine (Direct Modbus over Ethernet, e.g. FZ-94 Evo, is the one exception). And since this app can send real Burner/Air/Drum/Heater commands to a real, heat-producing machine, anyone who can reach it on your network can too, with nothing beyond the login screen in the way. Fine on a trusted home network; worth real thought anywhere less trusted.

Accounts and access

Opening the app for the first time shows a login/register screen — there's no built-in default account. The very first person to register becomes the admin, with immediate access; every account registered after that starts pending and can't log in until the admin approves it from the Manage Access page (only visible to the admin). From there the admin can Allow a pending registration, Deny one (pending or already-allowed — denying an already-logged-in user ends their session immediately, not just on their next login attempt), send a denied account back to pending for reconsideration, or Delete an account outright.

There's no per-feature permission system beyond this one gate — every allowed account, admin or not, has full access to everything else in the app (all roast modes, history, settings, automation rules). Sessions are a plain httponly cookie, not a token stored in the browser's own JS-accessible storage, and login persists across a backend restart (accounts and sessions are both in the same SQLite file as everything else, backend/data/roasts.db).

For calling the API directly — a script, a Home Assistant integration, curl — without going through the browser's cookie-based login at all, click your username in the header to open Account and generate an API key. Send it as an X-API-Key header; it's an alternative credential alongside the session cookie, not a replacement for it (the browser app itself keeps using cookies). The key is shown in full exactly once, right when you generate/regenerate it — only its hash is stored, so neither this app nor its database can show it to you again afterward. Regenerate replaces it (the old one stops working immediately); Revoke turns off API-key access entirely without issuing a replacement.

The Live Roast screen

Laid out like a roasting-scope screen: a toolbar with the title, ON/OFF device toggle + START recording button, and digital elapsed-time clock; vertical control sliders (Burner/Air/Drum, plus Burner SV in native °C for modbus_live) beside the banded live chart, with color-coded ET (crimson) / BT (blue) curves (their rates of rise drawn thin in the same colors on a 0–25 °/min axis; while recording, the time axis starts 30 seconds before Charge and shows ten minutes, and a finished roast fills the chart edge to edge; the temperature axis tops out at 350 °C / 527 °F unless the roast runs hotter; the Burner, Air and Drum lines, when shown, run low on the same axis on a 0–100 scale) and a matching ET/BT/ΔBT readout column; and the CHARGE/DRY END/FC START/FC END/SC START/DROP manual event-marker buttons underneath the chart. DRY%/»DRY/»FCs and other milestone-derived readouts are available as optional items in the configurable Breakout Panel (Settings) rather than a fixed row.

The data sources

Every roast is driven by one of these modes, picked from the Configure Roast form's "Data source" dropdown:

  1. Simulator — a small thermal model that generates realistic BT/ET/RoR curves and auto-detects roast events (turning point, dry end, first crack, drop). No hardware needed.
  2. .alog Playback — loads a real roast log and replays it at real (or accelerated) speed, including its events and notes. Also reads real-world .alog files, not just this project's own.
  3. Direct Modbus (USB or Ethernet) — talks straight to a real roaster's PLC over Modbus. Ships with defaults for Coffee-Tech's FZ-94 (USB/RTU) and FZ-94 Evo (Ethernet/TCP); every register is overridable for a different Modbus roaster. See docs/modbus/.
  4. Direct USB (thermocouple meter) — reads a Mastech MS6514 dual K-type thermocouple meter straight over USB-serial. Read-only (the meter has no command channel); T1 → BT, T2 → ET.
  5. Aillio Bullet (USB) — talks straight to a real Aillio Bullet over its own vendor-specific USB protocol (not Modbus/serial at all). Ships with the R1 model; nothing else to configure per-install (no port/host, the app finds it by its own USB id). See docs/aillio/bullet-r1.html.
  6. TC4+ (USB, aArtisanQ/PID firmware) — plain ASCII serial commands over USB to a TC4+ shield. Real Heater/Fan control (this hardware has no Drum channel at all); no feedback readback for either, so writes are fire-and-forget. DIY hardware with no single default wiring/config, so unlike the rest of these it has no built-in preset.

Every live-hardware mode leaves every milestone (Charge, Dry End, FC Start, and the rest) to the operator's own click by default, rather than guessing them from the temperature curve the way the Simulator does — live RoR is still computed and shown either way, to help time the click. Charge/Dry End/FC Start can optionally be switched to auto-detect from BT instead (Configure Roast form, opt-in, off by default) — manual clicks still work as an override even with that on. Turning Point always auto-fires either way; it's a pure observation (the BT minimum right after Charge), not a judgment call.

Clicking ON connects to the device and starts streaming live readings (nothing recorded yet); START begins actually recording that stream into a roast — for modbus_live/ms6514_live/aillio_live/tc4_live these are two genuinely separate steps (verify the connection before committing to a roast). For simulator/alog_playback, connecting and recording happen together in one step, since there's no real external connection to verify first.

Built-in presets

"Load saved config" entries the app ships with, so most people never type in a register map or port by hand. Alphabetical by preset name; tested on real hardware means actually connected to and verified against the physical device, not just protocol-level unit tests or a fake — everything else here is well-tested in every other sense (real end-to-end tests against hardware_fakes/, or thorough protocol-decoding pytest coverage for Aillio), just not yet against its real hardware.

More machine support is planned over time, covering a wide range of roasters/meters. In practice that mostly isn't new engine code: a new Modbus roaster model is usually just a new Device Profile (register numbers as data, not code); a genuinely different protocol (raw USB like Aillio, plain serial commands like TC4+) gets its own thin engine sharing the same core contract (tick/apply_command/status/close/is_finished) every other data source already implements. If your roaster or meter isn't listed above, it's very likely addable without a rewrite.

Saving a roast

Automatic — nothing extra to do. Click OFF once you're done: that stops the roast and writes its .alog file to backend/data/roasts/<roast_id>.alog, regardless of how it ends ("complete" if the engine itself signaled done, "stopped" if you clicked OFF yourself, "aborted" if something actually went wrong). To get the file:

  1. Click View detail (next to the toolbar once finished), or find the roast under History.
  2. Click Download .alog at the top of the detail page.

Testing without real hardware

Simplest: pick a simulated device in the app. In Configure Roast, under Device, the port (or host) field has a Try a simulated one link — for the FZ-94, FZ-94 Evo, MS6514 and TC4+. It fills in a sim://… value; connecting starts a built-in fake of that machine inside the server, so there is nothing to install or start, on Windows, macOS or Linux. The roast is marked Simulated, tagged simulated automatically, and left out of History's averages, so it never skews your real numbers. (The Aillio Bullet has no simulated device — it is a raw USB device.) While connected but not yet recording, a simulated machine holds at its Charge readings; its roast starts the moment you press START, so however long you spend checking the connection first, the recording begins at Charge.

simulator and alog_playback need nothing extra. For a developer who wants a fake running on its own (outside the app) or a real virtual serial port to test against, scripts/fake-hardware.sh fz94 (or ms6514 / tc4 / evo) starts one — see hardware_fakes/README.md for the full reference, including running it against an app on native Windows PowerShell.

Aillio Bullet (aillio_live) has no fake — it's a raw USB device, not a serial port or a TCP socket, and convincingly faking a real USB device needs kernel-level emulation well beyond what the other fakes need. It's still thoroughly covered by the backend's own pytest suite (pure protocol-decoding tests, no hardware involved), just not something you can click through in a running instance of the app without a real Bullet. See docs/aillio/bullet-r1.html.

Scripts reference

Everything in scripts/ and what each is for. Not sure where to start? install.sh (install.ps1 on Windows) once, then run-server.sh (run-server.ps1).

ScriptPlatformWhat it does
install.shmacOS, Linux/WSL2First-time setup, safe to re-run. Checks for Python 3.10+ and Node.js (offers to install them via brew/apt-get — asks first), creates .venv, installs the backend dependencies and the frontend's npm packages, and offers socat (only fake-hardware.sh needs it). --yes runs it unattended. Refuses to reuse a .venv created by native Windows Python, and says why.
install.ps1WindowsThe same, via winget; also offers to set up WSL2 for fake-hardware.sh if WSL2 is present. -Yes runs it unattended.
run-server.sh / run-server.ps1macOS, Linux/WSL2 / WindowsStarts the server (uvicorn) at http://localhost:8000, rebuilding the frontend first if it's out of date. Options: a port number (-Port), --reload (-Reload), --lan / --host (-Lan / -BindHost), --skip-build (-SkipBuild), --force-build (-ForceBuild).
fake-hardware.shWSL2, Linux, macOSStarts a fake roaster/meter (fz94, ms6514, tc4 or evo) so you can try the full connection path without real hardware, and prints the value to paste into the app. --help lists the options; --tcp bridges to an app running natively on Windows. Needs socat (except evo). See Testing without real hardware.
