Getting started

Setup and the run command differ slightly by platform — find yours below, then the rest of this page (accounts, data sources, saving a roast...) is the same regardless.

Setup & run

Prefer not to deal with a source checkout at all? See Standalone builds further down — a real double-clickable .exe/.app/Linux binary, no Python/Node/terminal involved at all. Building one still needs the dev setup below done once, on whichever machine builds it — but *running* it afterward, including for someone else you hand it to, needs nothing from this page.

Otherwise, from a terminal: scripts/install.sh once (or scripts\install.ps1 on Windows), then scripts/start.sh / scripts\start.ps1 — installs if this is a fresh clone, otherwise goes straight to the tray icon below.

Windows — PowerShell (native)

Only worth it for one specific reason: reaching a real roaster's actual COM port directly. WSL doesn't expose USB serial devices without extra tooling (usbipd-win), so if you're connecting to a real FZ-94 (or any real Modbus roaster) over USB, this is the recommended path over WSL2. 

cd roast-telemetry
scripts\install.ps1
scripts\run-server.ps1

install.ps1 installs Python/Node.js themselves too (via winget, asking first) if either is missing, then creates the venv and installs everything below — so this is the whole setup, not just a shortcut for part of it. It also offers to set up WSL2 (if present) for fake-hardware.sh, the fake-hardware testing tool — skipped automatically if WSL2 isn't installed; the app itself never needs it. Equivalent by hand: 

python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r backend\requirements.txt
cd frontend; npm install; cd ..
Note: if Activate.ps1 refuses to run ("running scripts is disabled on this system"), run once: Set-ExecutionPolicy -Scope CurrentUser RemoteSigned, then retry. Requires Python and Node.js installed natively on Windows — a venv created inside WSL only runs inside WSL (its files are Linux binaries), it's not usable from PowerShell even though the files are visible from Windows too if the repo sits under a Windows-mounted path.

scripts\run-server.ps1 takes the same options as the WSL2/Linux/macOS script below, PowerShell-flavored: -Port 7890, -Reload, -SkipBuild.

Windows (WSL2) / Linux

cd roast-telemetry
scripts/install.sh
scripts/run-server.sh

install.sh installs Python 3.10+/Node.js/socat themselves too (via apt-get, asking first) if any are missing, then creates the venv and installs everything below. Equivalent by hand: 

python3 -m venv .venv && source .venv/bin/activate   # first time only
pip install -r backend/requirements.txt               # first time only
cd frontend && npm install && cd ..                   # first time only

scripts/run-server.sh takes a port number (scripts/run-server.sh 7890, default 8000), --reload (auto-restart on backend code changes), and --skip-build (see the callout below).

Note: if this repo lives under a Windows-mounted path in WSL (e.g. /mnt/c/...), filesystem change events don't propagate to Vite's watcher, so Hot Module Reload can silently serve stale code after an edit. vite.config.js already sets server.watch.usePolling to work around this — if you still see stale behavior, restart npm run dev.

macOS

Same script as WSL2/Linux above (it detects macOS and uses brew instead of apt-get):

cd roast-telemetry
scripts/install.sh
scripts/run-server.sh

Equivalent by hand:

python3 -m venv .venv && source .venv/bin/activate   # first time only
pip install -r backend/requirements.txt               # first time only
cd frontend && npm install && cd ..                   # first time only

Real USB serial access (for a real roaster) works natively on macOS with no equivalent of WSL's USB-passthrough problem. For the fake hardware below, socat installs via brew install socat (or let install.sh offer to do it).

Whichever platform: open http://localhost:8000 — one process, one port. The API lives under /api/* on the same port (docs still at /docs), and any other path falls back to the React app's index.html so client-side routing (/roasts/:id, /compare, etc.) works on a hard refresh too.

Note: every one of these scripts rebuilds the frontend before starting by default, since the backend serves whatever's already sitting in frontend/dist/ and never rebuilds it for you — a stale build silently keeps serving old code with no error of any kind, including old login/auth behavior (this is a real thing that happened: an old pre-login build let anyone straight into the app with no login screen, even though the backend itself correctly rejected every API call underneath it). Pass --skip-build/-SkipBuild once you know your build is current, for faster restarts. Equivalent to running cd frontend && npm run build && cd .. && PYTHONPATH=. uvicorn backend.app.main:app --port 8000 by hand every time.

Tray icon (optional)

A system tray / menu-bar icon that starts and stops the server with a click, instead of a terminal command — works on Windows, macOS, and a real Linux desktop (not WSL2, which has no tray without WSLg; WSL2's own role stays the terminal-based install/fake-hardware workflow above, unchanged). scripts/install.sh/install.ps1 already install its dependencies (pystray, Pillow) by default, so there's no separate setup step — just run it: 

scripts/tray.sh      # Windows: scripts\tray.ps1

Or use the combined launcher (scripts/start.sh / scripts\start.ps1) — it installs first only if needed, then comes straight here.

Right-click the icon for Start/Stop/Restart/Open in browser. A color badge on the icon shows building (amber) / running (green) / stopped or crashed (gray/red) at a glance. The server's own output (started this way) goes to backend/data/server.log, appended across restarts, rather than to the console window, which would otherwise lose it once closed — Save logs... copies it wherever you choose (e.g. to send someone for troubleshooting).

The menu also has:

  • Port / Host — click either to change it (a text prompt, defaulting to 7890 / 127.0.0.1). Saved permanently, and if the server's already running, it restarts automatically so the change takes effect right away. 127.0.0.1 means this computer only; type 0.0.0.0 (or a specific address) for LAN access — see the LAN-exposure notes on this page before doing that for anything that actually controls a real roaster.
  • Copy URL to clipboard — the address to paste into another device's browser.
  • Rebuild frontend on start (checkbox, on by default) — same idea as --skip-build above, turn off once you know your build is current for faster restarts.
  • Launch at login (checkbox) — starts the tray automatically next time you log in (Windows Startup folder / macOS LaunchAgent / Linux autostart, whichever applies).

Standalone builds (no Python/Node install needed to run)

Everything above assumes running from a cloned repo with Python and Node installed. packaging/ builds a standalone, unsigned distributable instead — a folder (Windows/Linux) or a real .app (macOS) with the same tray icon experience as above, that someone else can just download and run with nothing else installed. Must be built natively on each target platform (there's no cross-compile path) — one command per platform, from a machine with this repo's own dev setup (install.sh/ install.ps1) already done: 

packaging\build-windows.ps1   # Windows, in PowerShell
scripts/build-macos.sh        # macOS
scripts/build-linux.sh        # Linux (needs a real desktop -- GTK/AppIndicator --
                               # to *run* the tray icon; the build itself works from WSL2)

Unsigned means a one-time OS warning on whoever's machine first runs it (Windows SmartScreen / macOS Gatekeeper) — expected, not a build error; see packaging/README.md for the exact click-through steps, what actually changes to make a frozen build behave correctly (per-user data directory, the server's own re-exec instead of shelling out to -m uvicorn), and what this does not do yet (code signing, a real installer, auto-update).

Two ports (for frontend development)

Use this instead when you're actively editing the frontend and want Vite's hot-reload rather than rebuilding on every change.

Backend

scripts/run-server.sh --skip-build --reload

(scripts\run-server.ps1 -SkipBuild -Reload on native Windows PowerShell.) --skip-build/-SkipBuild since Vite (not this backend) is serving the frontend here — nothing to build/serve from frontend/dist/ in this flow. --reload/-Reload auto-restarts the backend on backend code changes.

Docs at http://localhost:8000/docs. Roast data persists to backend/data/roasts.db (SQLite index) and backend/data/roasts/*.alog (full profiles). A pre-baked example lives at backend/data/sample_roasts/demo_roast.alog for exercising playback mode.

Frontend

cd frontend
npm install
npm run dev

Opens on http://localhost:5173 and proxies /api/* (including WebSockets) to the backend on port 8000 — see frontend/vite.config.js. Same on every platform.

The Live Roast screen deliberately mirrors Artisan desktop's own layout: a toolbar with the title, ON/OFF device toggle + START recording button, and digital elapsed-time clock; vertical control sliders (Burner/Air/Drum, plus Burner SV in native °C for modbus_live) beside the banded "Roaster Scope" chart, with color-coded ET (crimson) / BT (blue) curves and a matching ET/BT/ΔBT readout column; and the CHARGE/DRY END/FC START/FC END/SC START/DROP manual event-marker buttons underneath the chart. DRY%/»DRY/»FCs and other milestone-derived readouts are available as optional items in the configurable Breakout Panel (Settings) rather than a fixed row.

Accounts and access

Opening the app for the first time shows a login/register screen — there's no built-in default account. The very first person to register becomes the admin, with immediate access; every account registered after that starts pending and can't log in until the admin approves it from the Manage Access page (only visible to the admin). From there the admin can Allow a pending registration, Deny one (pending or already-allowed — denying an already-logged-in user ends their session immediately, not just on their next login attempt), send a denied account back to pending for reconsideration, or Delete an account outright.

There's no per-feature permission system beyond this one gate — every allowed account, admin or not, has full access to everything else in the app (all roast modes, history, settings, automation rules). Sessions are a plain httponly cookie, not a token stored in the browser's own JS-accessible storage, and login persists across a backend restart (accounts and sessions are both in the same SQLite file as everything else, backend/data/roasts.db).

For calling the API directly — a script, a Home Assistant integration, curl — without going through the browser's cookie-based login at all, click your username in the header to open Account and generate an API key. Send it as an X-API-Key header; it's an alternative credential alongside the session cookie, not a replacement for it (the browser app itself keeps using cookies). The key is shown in full exactly once, right when you generate/regenerate it — only its hash is stored, so neither this app nor its database can show it to you again afterward. Regenerate replaces it (the old one stops working immediately); Revoke turns off API-key access entirely without issuing a replacement.

The data sources

Every roast is driven by one of these modes, picked from the Configure Roast form's "Data source" dropdown:

  1. Artisan Simulator — a small thermal model that generates realistic BT/ET/RoR curves and auto-detects roast events (turning point, dry end, first crack, drop). No hardware needed.
  2. .alog Playback — loads a real roast log and replays it at real (or accelerated) speed, including its events and notes. Also reads genuine Artisan-exported .alog files, not just this project's own.
  3. Direct Modbus (USB or Ethernet) — talks straight to a real roaster's PLC over Modbus, bypassing Artisan entirely. Ships with defaults for Coffee-Tech's FZ-94 (USB/RTU) and FZ-94 Evo (Ethernet/TCP); every register is overridable for a different Modbus roaster. See docs/modbus/.
  4. Direct USB (thermocouple meter) — reads a Mastech MS6514 dual K-type thermocouple meter straight over USB-serial. Read-only (the meter has no command channel); T1 → BT, T2 → ET.
  5. Aillio Bullet (USB) — talks straight to a real Aillio Bullet over its own vendor-specific USB protocol (not Modbus/serial at all). Ships with the R1 model; nothing else to configure per-install (no port/host, the app finds it by its own USB id). See docs/aillio/bullet-r1.html.

Every live-hardware mode leaves every milestone (Charge, Dry End, FC Start, and the rest) to the operator's own click by default, rather than guessing them from the temperature curve the way the Simulator does — live RoR is still computed and shown either way, to help time the click. Charge/Dry End/FC Start can optionally be switched to auto-detect from BT instead (Configure Roast form, opt-in, off by default) — manual clicks still work as an override even with that on. Turning Point always auto-fires either way; it's a pure observation (the BT minimum right after Charge), not a judgment call.

Clicking ON connects to the device and starts streaming live readings (nothing recorded yet); START begins actually recording that stream into a roast — for modbus_live/ms6514_live/aillio_live these are two genuinely separate steps (verify the connection before committing to a roast), matching real Artisan's own connect-then-record model. For simulator/alog_playback, connecting and recording happen together in one step, since there's no real external connection to verify first.

Saving a roast

Automatic — nothing extra to do. Click OFF once you're done: that stops the roast and writes its .alog file to backend/data/roasts/<roast_id>.alog, regardless of how it ends ("complete" if the engine itself signaled done, "stopped" if you clicked OFF yourself, "aborted" if something actually went wrong). To get the file:

  1. Click View detail (next to the toolbar once finished), or find the roast under History.
  2. Click Download .alog at the top of the detail page.

Testing without real hardware

simulator and alog_playback need nothing extra — fully self-contained. Two of the three live-hardware modes (modbus_live, ms6514_live — see aillio_live's own note further down) can each be exercised end-to-end, through the app's actual connection code, using a fake standing in for the real device. The fake itself always runs via scripts/fake-hardware.sh in WSL2/Linux/macOS (it depends on socat, which doesn't exist on Windows, for the two serial-port-based fakes below — the Evo's own TCP fake needs no socat at all) — which flag you pass depends on where your app is running, not your own platform:

App running in WSL2/Linux/macOS (the WSL2/Linux/macOS setup above):

scripts/fake-hardware.sh fz94      # Coffee-Tech FZ-94, USB (Direct Modbus)
scripts/fake-hardware.sh evo       # Coffee-Tech FZ-94 Evo, Ethernet (Direct Modbus) -- no socat needed
scripts/fake-hardware.sh ms6514    # Mastech MS6514 meter (Direct USB)

Prints a /tmp/... serial port (or, for evo, a host/port) to paste into the app's Configure Roast form.

App running natively on Windows PowerShell (the Windows — PowerShell setup above) — run this in WSL2 instead, add --tcp:

scripts/fake-hardware.sh fz94 --tcp      # default port 5020
scripts/fake-hardware.sh fz94 --tcp 5030 # or a specific port

Prints a socket://127.0.0.1:<port> URL to paste instead — a WSL-internal /tmp/... path isn't reachable from a native-Windows process at all, so this bridges to a TCP listener over WSL2's own localhost port forwarding instead (pyserial treats that URL as a live serial connection; verified working end to end — both reads and writes — against a real Modbus client). evo's own fake already speaks real Modbus TCP, so it needs no --tcp bridging at all — it works the same way regardless of where the app runs.

Either way it cleans up after itself on Ctrl+C, and picks a fresh port name every run. See the project's hardware_fakes/README.md for what it's doing under the hood, or docs/modbus/fz-94-usb.html for the FZ-94 one specifically (the one that can also be controlled — Burner/Air/Drum — not just read), including options this wrapper doesn't expose (like a separate drive port).

Aillio Bullet (aillio_live) has no fake — it's a raw USB device, not a serial port or a TCP socket, and convincingly faking a real USB device needs kernel-level emulation well beyond what the other fakes need. It's still thoroughly covered by the backend's own pytest suite (pure protocol-decoding tests, no hardware involved), just not something you can click through in a running instance of the app without a real Bullet. See docs/aillio/bullet-r1.html.
