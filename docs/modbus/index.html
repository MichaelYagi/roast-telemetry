Direct Modbus Bridge

modbus_bridge (ModbusEngine) talks straight to a real roaster's PLC over Modbus RTU (USB/serial) or TCP (Ethernet), bypassing Artisan entirely. It can also control the roaster (Burner/Air/Drum), since that's just standard Modbus register reads and writes — alongside the Simulator and the Aillio Bullet (its own, genuinely different USB protocol — see docs/aillio/bullet-r1.html), the only live data sources that can; Direct USB (thermocouple meter) is read-only.

This page covers what's true for any Modbus-connected roaster. For a specific, already-confirmed model, see:

  • FZ-94 (USB) — Coffee-Tech Engineering's plain FZ-94, the only model this app ships defaults for today.

About to actually connect to a real machine? See the real-hardware checklist — pre-flight checks, the click-through sequence, and what to do afterward.

The register map is fully overridable

Nothing about the Modbus wiring is hardcoded to one machine. Every slave ID, register, and divisor ModbusEngine uses — BT/ET/DT/Burner's own, not just Air/Drum/Burner-range — is a constructor argument, and every one of those is in turn exposed as a per-roast override in the Configure Roast form's "Advanced Modbus register map":

ChannelWhat it needs
BT / ET / DTSlave ID, register, divisor (each independent)
BurnerSlave ID, register, divisor, plus the SV range (°C) the 0–100% UI slider maps onto
Air / DrumSlave ID, control register, frequency register, feedback register, plus the operating range in RPM (0–100/0–70 on the FZ-94, not a percentage)

Leave any of these blank to fall back to whatever defaults are configured for the selected model (FZ-94's, currently the only shipped set) — only worth touching once you've confirmed your own unit's actual register map genuinely differs, e.g. from the VFD drive's own nameplate/front-panel parameters, or a probe's real slave ID.

Device profiles

The 26 flat override fields above are one way to target a different Modbus roaster; a Device Profile is the other, more reusable way — a named, saved register map you pick from a dropdown instead of re-entering every field per roast. The Coffee-Tech FZ-94 ships as a built-in profile (not editable/deletable); anything else is a custom profile you build in the "Device profiles" panel of the Configure Roast form.

A profile has any number of temperature channels (role BT — always required, the heartbeat read — ET, DT, or any number of extra channels with their own label, e.g. "Flue") and any number of control channels, each mapped onto one of the three existing Controls-panel slots (Burner/Air/Drum) via one of three mechanisms:

MechanismWhat it is
Setpoint temperatureA bang-bang PID setpoint write+readback — the FZ-94's own Burner mechanism (see above): a drum-temperature limit, not a power percentage, mapped onto a configurable °C range for the 0–100% UI slider.
VFD driveA run/stop word plus a separate frequency-command register, optional feedback readback — the FZ-94's own Air/Drum mechanism.
Direct registerA single register directly holding a plain 0–100% value, one write, no run/stop word — the simpler mechanism plenty of non-FZ-94 roasters actually use for a fan or damper.

Extra temperature channels are recorded and shown on the live chart regardless of how many you declare, but only the first two (by declared order) round-trip through a saved .alog export — a fixed capacity in real Artisan's own native file format (its "extra device" bank has exactly 3 slots total; one is always reserved for DT), not an arbitrary limit. Anything beyond that stays live-only.

Connection basics that apply regardless of model

  • One serial connection usually handles everything — temperature probes, Burner, and the Air/Drum drives together, at whatever baud rate/framing the specific model uses (see that model's own page). A genuinely separate second connection (modbus_control_port) is supported for the uncommon case where a unit's own wiring splits drives onto a different physical link — leave it blank unless you've confirmed that's actually the case for your machine.
  • Mutually exclusive with anything else holding the same port — Modbus RTU assumes one master per bus. If Artisan (or any other software) is already connected to the same serial port, disconnect it first; two masters polling the same bus concurrently produces garbled reads on both sides, not a clean error.
  • ON connects and starts reading; START begins recording. These are two separate steps for Modbus specifically (see Getting started) — clicking ON opens the connection and streams live values immediately, with nothing recorded and no roast created yet; a Test Connection panel appears at that point to verify reads (and optionally one benign write) before you commit to an actual roast.
  • Controls only ever show the machine's real current state. Since Burner/Air/Drum are all genuinely read back from the PLC (not just echoed from the last command sent), connecting never writes a "starting value" on your behalf — the vertical control sliders beside the chart reflect whatever the roaster is actually doing (an operator's own manual setting, or state left over from a previous session), and nothing changes on the machine until you move a slider yourself.

Testing Mode

Once connected (armed — see above), a Test Connection panel appears with two options, meant for verifying a real connection is actually working before you commit to recording a roast:

  • Read-only — samples every configured channel (BT/ET/DT, Burner SV, Air/Drum feedback) for about 4 seconds and checks each one: is it present at all, is it within a plausible range (a loose sanity check against reading garbage or nothing, not a calibration check), and does it vary at all across samples (a real live reading almost always jitters slightly; dead-flat isn't necessarily wrong — fine if the roaster is genuinely idle — but worth a second look if you expected motion). A channel with no data at all shows a neutral warning, not a failure — most units don't have every channel wired (DT, for instance, is often absent), so "never populated" is frequently the correct shape, not a fault.
  • Read + write (only offered when the connection can write at all — a pure read-only meter like the MS6514 never gets this option) — does everything read-only does, plus one write check: reads Air's own current value and writes that exact same value straight back. On an idle machine (Air almost always already off) this is a genuine no-op — zero physical effect — while still exercising the real write path end to end and confirming the round-trip through the feedback register, not just that the call didn't error.

Burner is never touched by either check, automatically or otherwise — any nonzero setpoint can make the machine's own bang-bang controller start actually firing heating elements if DT reads below it, so it's excluded entirely, no exceptions. If the write check passes, an optional, separately-confirmed "nudge" is offered for anyone who wants a visible confirmation instead of just a silent round-trip — it bumps Air by 5 RPM for about 2 seconds, then sets it back, with its own explicit confirm step and up-front description of exactly what will happen before it runs. After the nudge, you're asked directly whether it actually moved (a register-level "done" only proves the feedback register echoed the commanded value, not that the fan physically spun) — answering "no" offers Drum as a differential test: same register numbers, same confidence level, different slave ID, so if Drum also doesn't visibly respond that's real evidence the shared register scheme itself is wrong for your unit, not something specific to Air.

None of this ever creates a roast record — the whole panel only exists during the armed-not-recording window, and both checks work purely through the same connection/command paths a manual slider adjustment (the vertical control sliders beside the chart) would use.

For the actual procedure — what to check before you even connect, and what to do once you're done — see the real-hardware checklist.

Automation rules (optional)

Every milestone (Charge, Dry End, First Crack, ...) is a plain manual click by default — see Getting started. You can optionally bind a Burner/Air/Drum command, an in-app banner message, or both, to fire automatically — matching what Artisan calls "Alarms." Configured per saved preset, from the "Automation rules" section of the Configure Roast form — it travels with "Save this configuration as," same as everything else in the form. Three trigger types:

  • Milestone — fires when a specific event is marked (Charge, Dry End, ...). Two examples: bind Drum speed to Charge so it's set the instant beans go in, or bind Burner/Air to Drop so the heat cuts and the cooling fan kicks on the moment you mark it.
  • Temperature — fires the first time BT or ET crosses a threshold you set (e.g. "BT ≥ 200°C"), checked every tick while actually recording. One-shot per roast — it won't re-fire on every later tick just because the temperature stays above the threshold.
  • Elapsed time — fires once a set number of seconds into the recording has passed, independent of any milestone or temperature. Also one-shot per roast.

Any rule can also add an extra delay (seconds) after its trigger condition is met before actually firing — e.g. "Charge, then wait 60 seconds, then Burner to 100%" for a soak period — and an optional banner message shown in-app the moment it fires (no sound, no browser push notification — just a visible, click-to-dismiss line on the Live Roast screen), independent of whether the rule also sends a command.

A rule can also chain into auto-marking a later milestone (the "Also mark milestone" dropdown) — e.g. "30 seconds after Turning Point, mark FC End" if you know your machine's development time is reliably consistent. This goes through the exact same path a manual button click uses, so it's still subject to every normal rule (can't mark something already marked, can't mark something out of sequence) — a rule that fires out of order just silently does nothing, the same tolerant failure as a bound command hitting a device error.

  • modbus_live only. ms6514_live has no write capability at all (a read-only thermocouple meter), so there's nothing to bind a command to.
  • Burner bindings need an extra confirm step when you add the rule — same caution as Testing Mode's write check above, since a bad Burner setpoint can make the roaster's own bang-bang controller start actually firing heating elements. Air/Drum-only (or message-only) rules save directly.
  • A delayed rule still pending when you click OFF/STOP is cancelled, not fired late — it never reaches a device that's already been disconnected.
  • A failed bound action (a device write error, or the roast having already ended) never fails the milestone click itself — the milestone is recorded either way; the control sliders reflect whatever the roaster's real state actually is either way, same as any other write.

Testing without real hardware

modbus_bridge can be exercised end-to-end — through the app's actual connection code, not a mock of it — against a fake standing in for the real PLC. See each model's own page for the specific fake and register values; FZ-94 (USB) → Testing without real hardware is the one currently available.
